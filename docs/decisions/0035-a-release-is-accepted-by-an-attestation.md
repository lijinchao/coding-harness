# 0035 — A release is accepted by an attestation, not by an order

Status: proposed

## Problem

The release is a protocol, and the operator's order is load-bearing: release the base, tag it, move the self pin and the example, re-record the proofs, push. Every step is checkable on its own — `release-ready` for undeclared recommended artifacts, `prove --check` for proof freshness, the full `prove` for the proofs themselves — but nothing binds them together, so a commit exists whose tag names a tool commit its proofs do not yet cover. This repository lived that state three times (0.1.28, 0.1.29, and this release line), and [direction.md](../direction.md) said "atomic publication" before the mechanism existed.

## Decision

A release is accepted when one artifact verifies. `harness attest --manifest <path>` writes a release attestation: the version, the commit the tag points to, the SHA-256 of the base release record, the self lock digest, the example lock digest, and the recorded proofs (gate, tool commit, definition hash). `harness attest --verify` recomputes every binding from the working tree and the tag and fails on any difference, so "this release is complete" is a checked claim rather than an order someone followed. The tag is announced only after the verification passes. This is `proposed`: the protocol above is what exists today, and the attestation is the next kernel change after the pack interface's contract is fixed.

## Alternatives

- Put proof freshness back inside a gate: refused twice already — a check that fails on stale records cannot be cleared by the run that refreshes them.
- Sign the attestation: signing proves who wrote it, not what it binds, and needs key material the harness does not manage; a hash binding is the part that closes this gap.
- Bind the committed proofs into the tag commit: impossible while the proof records the tag's own commit — the hash would have to contain itself.
- Leave it a protocol and document the order loudly: that is the state this record replaces, and it failed three times.

## Consequences

- A release becomes one verified artifact, and the intermediate commit stays visible in history without being announced.
- The attestation is a derived file: it lives under `dist/`, is regenerated by the command, and never becomes a second source of truth.
- Until it lands, the honest name is the release acceptance protocol, and direction.md says so.
