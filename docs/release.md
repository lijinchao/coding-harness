# The release protocol

A release is one transaction whose last step is a gate, and the honest name for what exists today is the **release acceptance protocol**: every step is checkable, and the operator owns the order.

## The order

1. Implement and test the change; run the full suite locally.
2. Bump `base/VERSION` and the product version, then `harness release --base base --out dist`.
3. Commit the release, `git tag v<version>`, and push the tag.
4. Move the pins: `harness upgrade --to <version> --tool-commit <release commit>` for the self harness and for the example.
5. Run every gate, then `harness prove --record` so each blocking gate carries a proof bound to the release commit.
6. `harness prove --check` and `harness doctor --strict` must both pass.
7. `harness attest`, then push.

Steps 1–6 are enforced where they can be: `release` fails when `dist` does not match `base/`, `prove` refuses to prove a gate whose record is stale, `doctor --strict` refuses an undeclared recommended artifact, and `release-ready` runs the last of those as a gate. Step 7 is the part that binds them.

## The attestation

`harness attest --manifest harness.manifest.json [--example <path>]` writes `dist/attestation-<version>.json`: the version, the release tag and the tool commit it points at, the digest of the base release record, the digest of the lock (and of a bound example manifest when given), and the proof set — each gate with the tool commit and definition hash it was proved against.

`harness attest --verify` recomputes every binding and fails on any difference, naming it: a tag that points somewhere else, a base release record that changed, a lock that moved, a proof set that no longer matches, or a proof bound to a tool commit other than the pinned one. A release is accepted when that verification passes.

The attestation is a derived snapshot, not a second source of truth: it is regenerated by the command and never hand-edited.

## Who attests

The attestation binds a repository to the release *it produces*: it needs the release tag `v<version>` in that repository, so it belongs to the repository that runs `harness release`, not to a consumer that pins someone else's base. The generated workflow therefore verifies an attestation when one exists and says so when none does, which keeps the step honest in both kinds of repository.
