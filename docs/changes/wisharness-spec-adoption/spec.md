- 已有需求、设计或契约引用：本仓 [delivery-flow 决策](../../decisions/0044-delivery-flow-starts-with-an-acceptance-map.md)、[现有 Pack 契约](../../../packs/delivery-flow/README.md)、[产品边界](../../direction.md)。借鉴来源为 `360MultiPaySdk_AS` 本地 `master@eaed603` 的 `.wisharness/templates/spec.md`、`.wisharness/templates/plan.md`、`.wisharness/rules/core.md` 和 `.wisharness/rules/method-design-planning.md`。
- 实施方案：[plan.md](plan.md)。本文件是后续迭代的 SPEC；本次提交不实现下述行为。

## 目标行为

- 用户或调用方在什么场景下，得到什么结果：对选择使用 `delivery-flow` 的复杂行为变更，项目先创建或复用一份行为真源，说明目标、当前差异、边界、正常与失败场景、验收及未决项；另用实施计划记录模块、顺序和验证。已有需求、契约或设计能够承担这些内容时，直接引用并在原处补齐。`delivery.plan.json` 作为机器验收映射，引用行为真源和已有测试，不复制第二份需求正文。普通局部修改不强制创建 spec/plan。
- 与当前行为的差异：当前 Pack 的 `design` 只检查所指文件非空，验收项 `description` 是独立文字；`verified` 检查计划摘要、测试冻结、回执及声明的 scope，却不要求行为真源在 scope 内或把其内容摘要纳入结果。因此行为正文在 scope 外变化可能不使原验证失效。现有 `tier_waivers` 只有 `tier` 和 `reason`，无法结构化区分“不适用”“尚未评估”“环境阻塞”。
- 期望的后续能力是一个**自愿采用**的 delivery-flow 新契约：行为真源必须是仓库内已跟踪文件，出现在声明的 scope 内；验证结果绑定其固定提交和内容摘要。每个验收项能引用行为真源中的稳定场景标识；机器检查引用存在且唯一，人的评审负责判断场景语义与测试是否充分。测试层级逐项报告 `covered`、`not_applicable`、`not_evaluated` 或 `blocked`，并保留具体理由与补验入口；后两者不得生成“已验证全部验收”的结论。

## 边界与非目标

- 适用范围、关键约束及异常或边界行为：
  - 范围限于后续可选的 `delivery-flow` Pack 与项目文档约定；不向所有仓库的内核 manifest 增加强制字段，也不把 SDK 项目的支付规则、Gradle 工程选择或 GitLab Issue 策略搬进共享 base。
  - 保留现有 `coding-harness.delivery/v1` 的读取语义；新字段和严格校验须通过新的契约版本或明确的 opt-in 启用，不悄然把历史 `tier_waivers` 当成已验证的不适用。迁移要给出旧计划到新计划的明确映射和拒绝条件。
  - 行为真源可为现有需求/契约/设计文件，文件名和目录由项目决定；新建时可参考 WisHarness 的 `spec.md`/`plan.md` 结构。验收场景正文只维护一处，计划只保存短摘要、稳定引用和检查映射。未解决的权限、兼容性或失败语义在真源中标明，不能以当前实现代替决定。
  - `covered` 只表示已声明检查且有对应有效回执；`not_applicable` 需要解释为何没有该类测试边界；缺 runner、环境、账号或命令执行失败属于 `blocked`，未调查属于 `not_evaluated`。单元、集成、E2E 各自报告，不互相代替；是否需要某层由真实场景决定。
  - 行为文档摘要、计划摘要、固定 Git revision 与回执必须绑定在同一候选；文档、测试、命令或候选 scope 变化使相关旧证据失效。机器只证明引用、版本和证据一致，不能证明场景完整、测试断言正确、人工验收或部署成功。
  - 现有 `command-review`、`delivery-flow`、`system-run` 和项目原生测试继续承担执行与回执；不新建重复执行器。外部服务、真实设备和凭据仍需项目授权与独立证据。
- 本次不处理的内容：不修改 WisHarness 插件或 `360MultiPaySdk_AS`；不自动判断需求复杂度、不生成产品语义、不强制全部项目采用模板、不自动创建 Issue/MR、不代替人工审批。此次文档提交也不启动 Pack v2 的实现或发布。

## 验收

- 以下场景是**后续实现的验收定义，当前尚未执行**；已有 Pack v1 的测试和报告不能充当这些场景的通过证据。

| 场景 | 入口与操作 | 预期结果 |
| --- | --- | --- |
| AC-01 复用项目真源 | 在已选择新契约的消费仓，计划引用现有需求文件及其场景标识，运行 planned 检查 | 有效引用通过；不生成、覆盖或复制第二份需求正文；简单任务未选择新契约时保持原有路径 |
| AC-02 引用缺失 | 删除行为文件、改成越界/未跟踪路径，或让验收项引用不存在/重复的场景，再运行 planned 检查 | 明确指出文件或场景问题，不能报告计划可用 |
| AC-03 需求漂移 | 在同一候选验证后修改行为正文，保持 `delivery.plan.json` 和测试不变，再检查旧回执 | 因行为文档摘要或 revision 不匹配而失效；不得沿用旧 `verified` 结论 |
| AC-04 分层真实状态 | 分别声明某层有检查、结构性不适用、未评估和环境阻塞，运行 planned/verified 检查 | 结果逐层呈现状态和理由；只有检查具有效回执或有具体不适用理由的层可满足该层；未评估/阻塞保留补验动作并阻止完整验证结论 |
| AC-05 兼容迁移 | 用原版 Pack 校验既有 v1 计划；再选择新契约尝试迁移缺少场景引用或把阻塞写成 waiver 的计划 | 原版行为不变；新契约明确拒绝不完整迁移，不静默提升旧声明的证据等级 |
| AC-06 实际消费 | 在一个具有真实跨模块变更与现有需求文件的消费仓运行命名测试、生成回执并检查最终 diff | 报告能把场景、分层检查、固定候选和未完成项追溯到真实文件；模拟数据只作为契约测试，不宣称跨仓或生产验收 |

- 尚未明确且会影响实现的行为及待澄清项：选择真实消费仓并复现一次“需求真源或验证层级被误判”的失败，再决定是否把新契约提升为 blocking gate；场景标识采用 Markdown 标题、显式锚点还是项目现有 ID；新契约版本与 v1 迁移工具的最小范围。未决项不影响本次 SPEC 归档，但影响后续实现。
